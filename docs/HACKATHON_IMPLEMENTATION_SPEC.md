状态：Approved for implementation

## 1. 要解决的问题

评委必须在一条连续链路中看懂并验证产品的独特价值：用户授权最小范围的行为数据，系统生成带来源的标签；匹配阶段不暴露可比较的个人资料；双方通过真实互动解锁共同点；关系可自然进入低压力的 3–10 人兴趣饭局。

成功不是“页面很多”，而是以下四个承诺同时成立：

1. **可信**：Live、Fixture、自填和推导数据可辨认，不伪造认证。
2. **克制**：匹配只展示一个分数、匿名代号和待解锁点，不泄露权重或资料。
3. **可推进**：聊天、任务和关系等级由双方行为驱动，单方刷消息无效。
4. **可落地**：饭局有安全门槛、状态机、匿名审核、群聊和商家权益闭环。

## 2. 范围

### P0

- 8 类自填标签，其中年龄和性别偏好是硬过滤；年龄偏好作为“年龄”字段的一部分。
- Duolingo / Keep Fixture 共生成至少 20 个规范化行为标签，并明确显示 `Fixture`。
- Duolingo public profile 提供一个无需凭据的只读 Live 同步路径；失败时不静默降级为 Live。
- 统一的服务端权重配置、相似度函数、分数排序和平滑展示。
- 匿名匹配、直接会话、30+ 任务卡、骰子、双向解锁任务、L0–L4 进度。
- C 端饭局创建、平台审核、报名、成团/取消/进行/结束/归档、匿名群聊。
- 2–3 个预置商家饭局、成团后权益、统一静态活动核销码和显式 Demo 核销。
- 手机验证 Demo 门槛、同性别局约束、举报、拉黑、CSRF、生产安全默认值。
- PRD 第 5 章的颜色、描边、硬投影、焦点态、响应式和 reduced-motion 规则。

### P1（只做高价值低风险项）

- 至少一个真实只读数据源：Duolingo public profile。
- 可复核的评委演示模式：只加速时间，不把模拟行为伪装成用户真实行为。
- CI、锁定依赖、声明清单和演示脚本。

### 明确不做

- Keep 真实登录或统计接口、Steam、WeRead、GitHub GraphQL。
- 商家自助后台、真实支付、POS、真实短信、真实二维码核销。
- V2 数据源和独立游戏房间。
- 为本次交付重写前端框架或拆分微服务。

## 3. 关键技术决策

### 3.1 保留 Flask SSR

现有 Flask + Jinja2 + SQLite 已覆盖完整用户链路。继续使用它能把时间投入到可信度、安全边界和演示稳定性，而不是框架迁移；对评委的直接影响是现场加载快、无构建依赖、页面刷新后状态仍在。

### 3.2 数据真相分层

每个标签必须带 `source`、`data_mode`、`verified`、`visibility` 和 `updated_at`：

- `self_reported`：用户自填，`verified=false`。
- `fixture`：确定性演示样例，`verified=false`。
- `live`：来自当前只读外部请求，`verified=true`。
- `derived`：由已有规范化标签推导，始终 `verified=false`，避免把解释性信号包装成上游事实。

Fixture 可以参与 Demo 匹配，但不得出现“已认证”“真实接口已接通”等文案。

### 3.3 外部请求采用标准库

Live MVP 只需要一个 GET 请求，使用 Python 标准库可减少供应链和部署风险。请求强制 HTTPS、用户名白名单、5 秒超时、256 KiB 响应上限、JSON 类型检查和稳定错误码；原始响应与访问凭据均不落库。

### 3.4 安全在服务端强制

所有状态修改请求验证 CSRF；活动创建检查手机号验证；报名检查活动状态、容量、时间冲突和同性别政策；消息/工具同时检查成员身份、拉黑、跨池和归档状态。UI 置灰只是提示，不能替代这些服务端约束。

### 3.5 关系进度采用共同活跃日

“聊满 N 天”定义为双方在同一自然日都发过文字消息的日期数量。L1 还要求双方都发言且总计至少 10 条。匹配点先创建协作任务，双方均在任务后回复才可揭示；Demo 快捷操作会被显式标注。

## 4. 数据与兼容策略

- SQLite 只做可回滚的增量迁移，不删除已有列。
- `users` 增加匹配年龄下限/上限。
- `external_connections` 和 `tags` 增加数据模式；旧演示数据迁移为 `fixture`，不得保留虚假的认证状态。
- 用户自填标签从 `users` 单一事实源动态生成，不复制存储。
- 历史 `access_token` 列保留兼容但清空且不再写入。

## 6. 主要风险与控制

| 风险 | 控制 | 用户/评委影响 |
| --- | --- | --- |
| Duolingo 非正式接口变更 | 稳定错误码、Fixture 回退入口、Live 不静默伪装 | 现场失败时仍可演示，且说法可信 |
| Fixture 被误认为真实数据 | 数据模式入库并在 UI 强标识 | 避免诚信扣分 |
| 安全修复破坏现有 harness | 先补边界测试，再逐项修改 | 演示链路保持稳定 |
| UI 多层样式互相覆盖 | PRD token 作为唯一根变量，聚焦核心组件 | 视觉统一且不做无关重构 |
| 时间加速破坏自然规则 | Demo offset 与自然进度分离 | 能现场展示 L4，又不污染产品语义 |

## 7. 完成定义

- P0 矩阵全部 `PASS`，或极少数外部依赖项明确标为 `FIXTURE`/`NOT AVAILABLE` 且不影响 Demo。

- 自动化、运行时、视觉和文档证据与最终提交 SHA 对齐。
