01 · WHY NOW

线上不敢信，线下没场景

线上社交有四个断点，第一条是需求本身被误解了。线下的需求则是已经被验证过的——大家早就在微信群和小红书自己找搭子了，只是没有产品在认真做。

线上 · 四个断点

  • 很多人不是来 dating 的，是来找倾诉对象的大部分女性用户的线上社交并不以恋爱为目的：现实压力想说说、好玩的事想分享、需要被理解和治愈。产品却默认所有人都在找对象。
  • 对方的数据不真实资料全靠自填，写「热爱运动」「正在学日语」零成本、零证据。用户有强烈的真实性验证需求，产品没给抓手。
  • 匹配后无法快速破冰匹配成功不等于关系开始。没有共同话题，双方都在等对方先说，绝大多数会话止于前三句。
  • 主流产品只会刷卡片放大的是照片、身高、学校。选择悖论：可选项质量提升不会提高满意度，只会抬高标准 —— 看得越多，越挑，越不满意。

线下 · 需求真实，但没人在做

  • 用户早就在自己找搭子了微信群、小红书上到处是「找饭搭子」「找学习搭子」的帖子。需求已经被验证，但渠道分散、效率极低、也没有任何信任机制。
  • 一个人吃饭没意思，想认识同好却缺场景刚到新城市、独居、周末想约饭凑不齐人 —— 缺的不是匹配算法，是一个能坐下来的场景。
  • 餐厅的空桌也没人管非高峰时段空桌率高，线上获客成本又贵。餐饮毛利率高，愿意用套餐让利换客流，但缺少把「一群精准的人」凑到店里的工具。

国内现状：美团点评解决「去哪里吃」，不解决「和谁吃」；探探陌陌解决泛社交，但饭局场景弱、信任感差；微信群和豆瓣小组有需求但分散低效、无信任机制。目前没有一个有强心智的「饭局社交」品牌。

02 · THE LOOP

线上建立信任，线下落地关系

这不是四个并列的功能，而是两个板块构成一个闭环。两边侧重点完全不同，但共用同一套真实标签体系。

线上 · 1 对 1 · 全程匿名

  • 解决「信不信」标签从多邻国、Keep 自动生成，不是自填
  • 解决「怎么选」只给一个匹配度数字，规避选择悖论
  • 解决「聊什么」破冰工具箱把话题变成按提示做
侧重点

把陌生人之间的信任建立起来。慢、深、一对一。

线下 · 3–10 人 · 兴趣局

  • 解决「关系往哪去」多人局替代 1V1 见面，压力被人数分散
  • 钩子是共同兴趣「都对 AI 感兴趣」「都在创业」，话题天然存在
  • 带商业闭环餐厅让利换客流，用户拿折扣
侧重点

把线上关系落到现实。快、轻、多人群组。

  1. 1真实标签自动生成
  2. 2匿名匹配只给百分比
  3. 3破冰聊天渐进解锁
  4. 4报名兴趣局3–10 人成团
  5. 5线下见面关系落地
  6. 6回到 1V1 会话闭环，重新开始
03 · ONLINE ①

标签不是填的，是从你用的 App 里长出来的

五个数据源，覆盖学习、运动、音乐、阅读、代码五类真实行为。接口层与数据层解耦，统一 DataSourceAdapter 抽象，字段结构、鉴权流程、错误码全部按真实接入设计。

五个数据源 · 标签自动生成

  • 多邻国在学语种、连续打卡 971 天、学习时段、等级
  • Keep运动类型、周频次、累计里程、晨练还是夜跑
  • 网易云音乐音乐口味、常听歌手与歌单、深夜听歌习惯
  • 微信读书在读书单、阅读品类、读书时长与完读本数
  • GitHub技术栈语言、提交频率、开源参与、深夜提交

跨源复合标签 · 真正的差异化

  • 自律程度多邻国打卡 + Keep 打卡 + GitHub 提交，三个源一起算
  • 活跃时间重叠度学习、运动、听歌、提交时段交叉，得出真实作息画像
  • 兴趣纵深不只是「喜欢音乐」，而是听什么、读什么、写什么语言
  • 目的一致性自填目的与行为数据是否自洽，可做可信度徽标

注册时另填 8 个基础标签兜底，没授权任何 App 也能完成匹配。每个标签都带 source 来源徽标，前端展示「来自网易云音乐」——这是真实性唯一的可视化证明。所有标签 visibility: self_only，只有本人可见。

附录 A1 · ALGORITHM

匹配度计算四步

  1. 第一步

    硬性过滤

    按年龄区间、希望匹配性别过滤候选池。

    不占权重
  2. 第二步

    逐标签打分

    对候选池每个用户计算 sim_i ∈ [0,1]。

    6 种类型
  3. 第三步

    加权求和

    匹配度 = Σ(w_i × sim_i) × 100%，其中 Σw_i = 1。

    合计 100%
  4. 第四步

    展示平滑

    原始分映射到 60%–98% 区间后展示，避免 12% 这类挫伤体验的低分。

    排序仍按原始分

附录 A2 · WEIGHTS

权重是后端参数，不是用户功能

100% 按比例分配到各标签，写在统一配置文件里。用户端没有任何权重配置入口：没有配置页、没有滑块、没有拖拽格子。取值后续靠 A/B 测试选优，本次 Demo 用固定权重。

  • 交友目的30%自填 · 目的不一致，其他维度再像也聊不下去
  • API 行为标签25%多邻国 / Keep · 差异化卖点必须有话语权
  • 兴趣爱好20%自填 · 共同话题的直接来源
  • 活跃时间重叠度15%自填 + API 复合 · 隐性但强相关
  • 城市5%匿名线上为主，同城不是刚需
  • MBTI5%弱信号，只做微调

兜底规则

未授权任何第三方 App 时，行为标签的 25% 按 30:20 回补到交友目的与兴趣爱好 → 交友目的 45% + 兴趣爱好 30% + 时间重叠 15% + 城市 5% + MBTI 5%。

研发要求

权重集中在 matchWeights.config.ts，禁止散落硬编码；预留 groupKey 对应交友目的；启动时断言各组权重之和等于 1。

附录 A3 · SEARCHING

三阶段过程动画，状态机在服务端

  1. 260ms硬性筛选年龄区间 · 希望匹配性别
  2. 1000ms相似度计算逐标签 sim_i 打分
  3. 1740ms匿名排序按原始分排序
  4. 2500ms完成POST /matches/search/complete

前端只管时序

前端只控制展示时序与提交普通 POST 表单。候选选择、尝试令牌、取消、旧页面失效、结果确认全部由服务端状态机处理。

降级路径

无 JavaScript 时可直接提交「查看结果」；prefers-reduced-motion 下立即完成步骤。匹配中 HTML 不含候选 ID、代号、分数、标签或结果 JSON。

附录 A4 · PRIVACY & SAFETY

平台永不主动替用户揭面

线下见面必然要露脸，和匿名机制存在天然冲突。这里定一套明确规则，研发不要自行推断。

标签可见性契约

  • 用户看自己全部展示，要看到自己有哪些标签
  • 看匹配对象（匹配阶段）不展示，只给匹配度百分比
  • 看匹配对象（聊天阶段）按 L0–L4 解锁进度逐步展示
  • 任何人看权重规则永不展示，产品内也不解释比例
  • 线下约饭场景报名只见匹配度与共同标签数量
「我导进来的数据只对我展示，不会对别人展示。」会议原话 · 决策 #2

线下安全机制 · 全部 P0

  • 地点限定只能选真实餐厅 POI，禁止私人住址、KTV 包房等封闭场所
  • 实名门槛发起线下活动需手机号验证；商家需资质审核，Demo 可 mock
  • 性别构成透明报名前可见当前性别比例，支持仅同性别局
  • 举报入口活动页与群聊内均有举报入口
  • 成团后可见群聊内只有匿名代号 + 1–2 个兴趣标签，用于破冰
  • 线下见面现实中自然可见，平台内资料仍不主动展示

核心原则

线下见到的是现实，平台内的资料解锁仍然由聊天进度决定。两套逻辑互不干扰。
